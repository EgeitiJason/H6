1  Summary and design

This guide adds 802.1X port authentication, with MAC Authentication Bypass (MAB) as a fallback, to the access ports on both access switches. PacketFence (SRV-RADIUS-01) is the RADIUS server. It decides which VLAN each device gets:

Device / situationHow it authenticatesResult
Domain user or computer802.1X (PEAP-MSCHAPv2) against AD mfrace.internalRole default → VLAN 20 Klienter
Unknown or unregistered deviceMAB (MAC address)Role registration → VLAN 555 (captive portal)
Device that breaks policy802.1X or MABRole isolation → VLAN 666 Jail
UniFi access point (one per site, Gi1/0/45)MAB, MAC registered in PacketFenceRole unifi_ap. PacketFence pushes the interface template PF_UNIFI_AP, which turns the port into a trunk (native 99, tagged 20)
PacketFence unreachable–Critical authorization → VLAN 20 (users can keep working)

1.1  Design decisions

  • OPNsense stays the only router. The DSWs only switch. The registration and jail networks get CARP gateways on the OPNsense HA pairs, just like the existing VLANs.
  • Middelfart is layer 2 to PacketFence. PacketFence has its own interfaces in VLANs 555 and 666 at DC1 and serves DHCP and DNS there directly.
  • Odense is routed. The Odense firewall relays DHCP to PacketFence over the existing route-based IPsec tunnel (ipsec10).
  • New per-site subnets: registration 10.0.55.0/24 / 10.10.55.0/24, jail 10.0.66.0/24 / 10.10.66.0/24.
  • IBNS 2.0 (new-style) on the ASWs. It's needed so PacketFence can push an interface template to the AP port. It also makes the port policy clearer.
  • Existing RADIUS group. The ASWs already use SRV-RADIUS → 10.0.10.16 for VTY login. 802.1X reuses this group and leaves login untouched.

4.5  Active Directory source and 802.1X

The AD source mfrace already exists (LDAPS, srv-adds-01/02.mfrace.internal, base DN DC=mfrace,DC=internal), and PacketFence is joined to the domain MFRACE. Add or check the authentication rule:

Rule (class: authentication)ConditionActions
catchall in source mfracematch allRole = default, Access duration = 1 day (reauthentication renews it)

Realms (required). Windows sends the user as MFRACE\user. PacketFence only strips the domain for realms it knows, so without these the AD lookup searches for sAMAccountName=MFRACE\user, matches nothing and the login is rejected. Under Policies and Access Control → Realms create MFRACE and mfrace.internal, both with domain mfrace and Strip on RADIUS authorization enabled, and list them as the source's associated realms.

Computer authentication. A computer authenticates as host/PC.mfrace.internal, which no AD account carries as its name. Add dNSHostName to Search Attributes on the mfrace source, otherwise no rule matches and every PC is rejected before a user logs in.

Then create a connection profile under Policies and Access Control → Connection Profiles:

4.6  UniFi AP: node and RADIUS filter

  1. Nodes → Create: MAC 9c:05:d6:ba:c1:c9 (Middelfart AP, seen on NW-ASW-DC1-01 Gi1/0/45). Status registered, role unifi_ap, unregistration date none, notes "UniFi AP DC1".
  2. Look up the MAC of the Odense AP in the UniFi controller (SRV-UNIFI-01) and register it the same way. It isn't connected today.
  3. Configuration → Advanced Access Configuration → Filter Engines → RADIUS Filters: add the filter below. Or add it to /usr/local/pf/conf/radius_filters.conf and run pfcmd configreload hard.
[UNIFI_AP_TEMPLATE]
status=enabled
description=Push the PF_UNIFI_AP interface template to UniFi AP ports
top_op=and
condition=node_info.category == "unifi_ap"
scopes=returnRadiusAccessAccept
merge_answer=yes
answer.0=Cisco-AVPair = interface-template-name=PF_UNIFI_AP
Security noteMAB only checks a MAC address, and MAC addresses can be spoofed. Anyone who copies the AP MAC and plugs into an access port gets a trunk to VLANs 20 and 99. Keep the AP ports physically secured. If that's not good enough, use the static fallback in §10.4 and restrict it with port security.

10  Automatic AP port configuration

Goal: when a UniFi AP is plugged into any 802.1X port (normally Gi1/0/45), the port automatically becomes a trunk with management untagged on VLAN 99 and wireless clients tagged on VLAN 20. This matches today's manual config on NW-ASW-DC1-01 Gi1/0/45.

10.1  How it works

  1. The port starts with template PF_ACCESS. The UniFi AP doesn't speak 802.1X, so after about 10 seconds the switch falls back to MAB.
  2. PacketFence recognises the MAC as a registered node in role unifi_ap. The RADIUS filter UNIFI_AP_TEMPLATE (§4.6) adds Cisco-AVPair = interface-template-name=PF_UNIFI_AP to the Access-Accept.
  3. The switch binds the dynamic template PF_UNIFI_AP to the port. It does not replace PF_ACCESS: the two are merged, and the dynamic template wins wherever both set the same command. That is why PF_UNIFI_AP has to set access-session host-mode multi-host. With the single-host from PF_ACCESS still in force, the first Wi-Fi client behind the AP counts as a second MAC, triggers a security violation and the trunk never comes up.
  4. Do not use access-session port-control force-authorized in the AP template. It ends the authentication session, the session was what bound the dynamic template, so the port falls back to PF_ACCESS and the whole thing loops every 40 seconds.
  5. The port itself must carry no switchport commands. Settings written on the interface beat any template, so run default interface before source template PF_ACCESS. A leftover switchport mode access keeps the port an access port for ever.
  6. access-session interface-template sticky keeps the template bound while the link stays up. If the link goes down (AP unplugged), the port returns to PF_ACCESS after 30 seconds, so a different device in that port goes through 802.1X/MAB again.

10.4  Fallback: static AP port

If the pilot shows the dynamic template doesn't bind on your IOS release, configure the AP port statically and leave it out of 802.1X. Port security limits it to the AP's MAC:

default interface GigabitEthernet1/0/45
interface GigabitEthernet1/0/45
 description UniFi AP (static, excluded from NAC)
 switchport mode trunk
 switchport trunk native vlan 99
 switchport trunk allowed vlan 20,99
 switchport port-security maximum 1 vlan access
 switchport port-security mac-address sticky
 switchport port-security violation restrict
 switchport port-security
 spanning-tree portfast trunk

With port security on a trunk, the AP's own MAC is learned on the native VLAN. Wireless clients (VLAN 20) aren't limited. If you use this fallback, test it with the AP connected before you rely on it.

11  Windows clients (Group Policy)

Users sign in with 802.1X (PEAP-MSCHAPv2) using their MFRACE AD credentials. Deploy the settings with a GPO linked to the OUs that contain the computers:

SettingValue
System Services → Wired AutoConfig (dot3svc)Automatic
Security Settings → Wired Network (IEEE 802.3) PoliciesNew policy MFRACE-Wired, Use Windows Wired Auto Config enabled
Network authentication methodMicrosoft: Protected EAP (PEAP)
Verify the server's identity with its certificateEnabled. Connect to servers: srv-radius-01.mfrace.internal
Trusted Root CAYour AD CS root CA (the CA that issued the certificate in §4.7)
Inner methodSecured password (EAP-MSCHAP v2), Automatically use my Windows logon name and password
Authentication modeUser or computer authentication
Why "user or computer"The computer authenticates at boot, so domain logon, GPO processing and login scripts work before a user signs in. Once the user signs in, the connection re-authenticates as that user. PacketFence gives both the default role (VLAN 20).
Fallback when PacketFence is unreachableWithout it the critical VLAN (§9.3) does not help: the switch authorizes the port in VLAN 20, but Windows sees Authentication failed and blocks the connection itself, so the PC has an address and still reaches nothing. The setting is called Fallback to unauthorized network access (OneXEnforced=false in the profile). The GPO wired policy does not expose it: it only exists on the adapter's Authentication tab and in a LAN profile XML. Deploy it as a LAN profile instead: build the profile on one PC, export it with netsh lan export profile, and apply it at boot with a startup script (netsh lan add profile filename=… interface=…), or use docs/wired-dot1x/New-MFRACEWiredProfile.ps1 from the repository, which builds the profile from the PC's own certificate store. A GPO wired policy always overrides local profiles, so remove the policy if you deploy profiles this way. Run the script elevated (SYSTEM in a startup script), otherwise you get a user profile and the machine profile needed for authentication before logon is missing.
EAP-TLS or PEAPBoth work against this PacketFence. PEAP-MSCHAPv2 needs no client certificate, but Credential Guard (on by default in Windows 11 Enterprise/Education 22H2+) blocks single sign-on with it, and the PC then quietly falls back to MAB. EAP-TLS with a computer certificate from MFRACE-Issuing-CA avoids that and sends no passwords. Whichever you choose, use the same one everywhere, and check sc query dot3svc: with the Wired AutoConfig service stopped the PC never answers EAPOL at all and lands on MAB.

Devices that can't do 802.1X, such as printers, register through the captive portal, or an admin registers them by MAC in PacketFence with the role they need.
